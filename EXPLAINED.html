peershare (Python) — explained from the ground up

This is a worked walkthrough of peershare-py: every class, every function, the README, and the reasoning behind each design choice. It's organized like a worked math problem — code first, then numbered steps explaining exactly what happens and why it was built that way.

1 Big picture

peershare does two completely different jobs, and it's important to keep them separate in your head:

  1. An HTTP API (port 8080) that the Next.js UI talks to — upload a file, get back a port number.
  2. A raw TCP file-transfer protocol — a one-shot, one-file mini-server that opens on that port number so a second person (the "peer" — could be your phone, could be a friend) can connect directly and stream the file down, with no HTTP involved at all.

The "invite code" you see in the UI is the TCP port number. That's the whole trick of this project.

┌─────────────┐ POST /upload (multipart) ┌──────────────────────────┐ │ Browser / │ ──────────────────────────────────────▶│ peershareRequestHandler │ │ Next.js UI │ │ (http.server, :8080) │ │ │ ◀────────────────────────────────────── │ saves file, picks port │ └─────────────┘ { "port": 51263 } └──────────┬───────────────┘ │ offer_file() / start_file_server() ▼ ┌──────────────────────┐ │ FileSharer │ │ raw socket.socket() │ │ listening on :51263 │ └──────────┬────────────┘ │ "Filename: x\n" + raw bytes GET /download/51263 │ ┌─────────────┐ (browser asks the API server, │ │ Peer / │ which then opens a *second*, plain │ │ phone │ TCP socket to localhost:51263 ▼ │ │ on the API's behalf) ┌─────────────────────────────┐ └──────┬───────┘ ◀─────────────────────────────────────│ socket.connect(("localhost",│ │ raw file bytes, streamed │ 51263)) │ ▼ └─────────────────────────────┘ saved file
Why two protocols instead of just serving the file over HTTP?
The project exists to teach raw socket programming and a hand-rolled wire protocol, not to be the most efficient file-sharing app. Splitting "control plane" (HTTP: who, what, give me a port) from "data plane" (raw TCP: just send me the bytes) is also a real pattern used by protocols like FTP and BitTorrent.

2 README, explained

The README is short on purpose — it's a table of "what's hand-rolled vs. what's stdlib," plus run instructions. Here's what each row actually buys you:

README claimWhat it really means
http.server.HTTPServer + BaseHTTPRequestHandler We didn't write our own HTTP request-line/header parser. Python's stdlib already has one built in (just like the Java original leaned on the JDK's com.sun.net.httpserver.HttpServer instead of parsing HTTP by hand). The thing we do write ourselves is everything inside each handler method.
Custom ThreadPoolHTTPServer http.server by default handles one request at a time on the main thread. We override process_request so each connection is handed to a fixed pool of 10 worker threads — manually replicating Java's Executors.newFixedThreadPool(10) rather than using Python's built-in socketserver.ThreadingMixIn (which spawns an unbounded number of threads — one per request, no cap).
Hand-rolled multipart parser No cgi, no email.parser, no python-multipart. We manually search the raw request bytes for filename=", Content-Type:, and the MIME boundary marker. This is the part of the project that's specifically about understanding how a file upload is actually encoded on the wire.
Raw-socket P2P transfer The actual file bytes never touch the multipart parser or HTTP server again after upload. A brand new socket.socket() is opened on a random high port, and bytes are pushed down it with a single custom text header in front.

Run instructions

python app.py

Starts the API on port 8080. Because the endpoints (POST /upload, GET /download/{port}) match the original Java API exactly, the existing Next.js frontend in ../peershare-main/ui needs zero changes — its next.config.js rewrites already point at http://localhost:8080.

Bug fixed during the port
Java's UploadUtils.generateCode() computed random.nextInt((DYNAMIC_ENDING_PORT - DYNAMIC_STARTING_PORT) + DYNAMIC_STARTING_PORT). Walk the arithmetic: that's nextInt(65535), which returns a value in [0, 65535) — not restricted to the intended 49152–65535 "dynamic/private" port range at all. It could hand out port 80, port 22, or port 0. The Python version fixes this with random.randint(49152, 65535), which is properly bounded on both ends. See §3.

3 p2p/upload_utils.py

The smallest file in the project — one job: generate a random "invite code" (which, recall, is literally a TCP port number).

import random

DYNAMIC_STARTING_PORT = 49152
DYNAMIC_ENDING_PORT = 65535


def generate_code() -> int:
    """Pick a random port in the dynamic/private port range (49152-65535)."""
    return random.randint(DYNAMIC_STARTING_PORT, DYNAMIC_ENDING_PORT)
Step 1 — why 49152–65535 specifically?
These are the dynamic/private/ephemeral
Step 2 — random.randint(a, b) is inclusive on both ends
Unlike Java's Random.nextInt(bound) (which is exclusive of bound and starts at 0), Python's randint(a, b) returns a value where a <= x <= b. That's exactly the semantics we want here — no off-by-one translation needed, which is precisely where the original Java code went wrong (see the bug box in §2).
Why is this its own tiny module instead of inline code?
Mirrors the original Java structure 1:1 (UploadUtils.java) so the port stays easy to compare line-by-line against the source project, and so FileSharer doesn't need to know anything about port-range constants.

4 p2p/file_sharer.py

This is the data-plane half of the app — the raw-socket file server. No HTTP anywhere in this file.

The class and its state

class FileSharer:
    """
    Hands out a one-time-use port for each uploaded file, then runs a
    tiny raw-socket file server on that port so a peer can connect and
    stream the bytes down directly (no HTTP involved in the transfer).
    """

    def __init__(self):
        self.available_files = {}
Step 1 — the registry
available_files is a plain dict mapping port number → absolute file path on disk. One FileSharer instance lives for the lifetime of the server process (it's created once in FileController.__init__), so every upload during that process's life adds one more entry.

offer_file — claim a free port

def offer_file(self, file_path: str) -> int:
    while True:
        port = upload_utils.generate_code()
        if port not in self.available_files:
            self.available_files[port] = file_path
            return port
Step 1 — generate, then check
Roll a random port via upload_utils.generate_code().
Step 2 — collision retry loop
If that port is already claimed by a different file (rare, but the random range is only ~16,000 wide), loop and roll again. This is a classic "optimistic retry" pattern — cheap because the collision probability is low, so an infinite loop in practice runs once or twice.
Step 3 — register and return
Once a free port is found, it's immediately reserved in the dict (so a second concurrent upload can't pick the same one) and handed back to the caller — which, in file_controller.py, is what gets JSON-encoded as {"port": N} and shown to the user as the invite code.

start_file_server — the one-shot TCP listener

def start_file_server(self, port: int) -> None:
    file_path = self.available_files.get(port)
    if file_path is None:
        print(f"No file associated with port: {port}")
        return

    server_socket = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    server_socket.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    try:
        server_socket.bind(("", port))
        server_socket.listen(1)
        print(f"Serving file '{os.path.basename(file_path)}' on port {port}")

        client_socket, client_address = server_socket.accept()
        print(f"Client connected: {client_address[0]}")

        threading.Thread(
            target=self._send_file,
            args=(client_socket, file_path),
            daemon=True,
        ).start()
    except OSError as e:
        print(f"Error starting file server on port {port}: {e}")
    finally:
        server_socket.close()
Step 1 — look up the file, bail if it's gone
If the port isn't in the dict (already consumed, or never existed), log and return. No exception, no crash — this runs on a background thread so there's nobody waiting on a return value anyway.
Step 2 — socket.socket(AF_INET, SOCK_STREAM)
This is the raw building block: AF_INET means "IPv4 address family," SOCK_STREAM means "TCP" (as opposed to SOCK_DGRAM for UDP). This single line is the entire reason the project avoids a web framework for this part — frameworks hide exactly this object.
Step 3 — SO_REUSEADDR
Without this, rapidly restarting the app could fail to rebind a port still lingering in the OS's TCP TIME_WAIT state from a previous connection. It tells the OS "let me reuse this address even if a previous socket on it hasn't fully closed out yet."
Step 4 — bind then listen(1)
bind(("", port)) attaches the socket to "all network interfaces" on that port. listen(1) turns it into a passive listening socket with a backlog queue of just 1 — deliberate, because this is a one-shot server: exactly one peer is expected to ever connect to this specific port for this specific file.
Step 5 — accept() blocks until a peer connects
Execution stops here until someone (the download handler in §6.4) opens a TCP connection to localhost:<port>. This is why start_file_server itself is launched on its own background thread from file_controller.py — if it ran on the HTTP handler's thread, the upload response would hang until someone downloaded the file.
Step 6 — hand the connected socket to _send_file, on yet another thread
Once a peer connects, sending the actual bytes is delegated to a second background thread so start_file_server can immediately fall through to its finally and close the now-unneeded listening socket (not the client connection — that's a separate socket object handed to _send_file).

_send_file — the wire protocol

@staticmethod
def _send_file(client_socket: socket.socket, file_path: str) -> None:
    filename = os.path.basename(file_path)
    try:
        header = f"Filename: {filename}\n".encode("utf-8")
        client_socket.sendall(header)

        with open(file_path, "rb") as f:
            while True:
                chunk = f.read(4096)
                if not chunk:
                    break
                client_socket.sendall(chunk)

        print(f"File '{filename}' sent to {client_socket.getpeername()[0]}")
    except OSError as e:
        print(f"Error sending file to client: {e}")
    finally:
        client_socket.close()
Step 1 — the entire "protocol" is one text line
b"Filename: cat.png\n" is sent first, raw, with no length prefix and no Content-Type — just enough for the receiver to recover the original filename. This is the project's hand-rolled equivalent of an HTTP header, except there's exactly one of them and it's terminated by \n instead of \r\n\r\n.
Step 2 — stream the file in 4 KB chunks
Reading the whole file into memory with one f.read() would work for small files but defeats the purpose of "streaming" — and would blow up memory for large files. 4096 bytes (one typical OS page / disk block size) is the classic buffer size for this kind of loop.
Step 3 — sendall vs send
Plain socket.send() is allowed to write fewer bytes than you asked (a partial write) and returns how many it actually sent — you'd have to loop and retry yourself. sendall() does that retry loop internally and only returns once everything is sent (or raises). Using it here is intentional correctness, not a shortcut — the manual byte-loop is still fully visible in the 4096-byte read loop above it.
Step 4 — always close the socket
The finally guarantees the TCP connection is torn down whether the transfer succeeded or an OSError (e.g. peer disconnected mid-transfer) interrupted it.

5 p2p/multipart_parser.py

This is the file most worth slowing down on, because it's solving a problem most developers never see solved manually: how is a file upload actually encoded inside an HTTP request body?

Background: what does a multipart/form-data body actually look like?

When a browser uploads a file via a <form> or FormData, the request body is not just the raw file bytes — it's wrapped in a text-based envelope that looks like this (boundary string shortened for readability):

--BOUNDARY Content-Disposition: form-data; name="file"; filename="cat.png" Content-Type: image/png <raw bytes of cat.png here> --BOUNDARY--

The parser's whole job is to locate four things inside that envelope: the filename, the Content-Type, where the headers end and raw bytes begin, and where the raw bytes end (the boundary line).

from dataclasses import dataclass
from typing import Optional


@dataclass
class ParseResult:
    filename: str
    content_type: str
    file_content: bytes
Step 1 — ParseResult is just a typed tuple
@dataclass is stdlib sugar that auto-generates __init__, giving us ParseResult(filename, content_type, file_content) for free — this is bookkeeping, not part of the "from scratch" parsing logic, so using the stdlib decorator here doesn't cut any corners that matter. 
def parse(self) -> Optional[ParseResult]:
    try:
        header_end_marker = b"\r\n\r\n"
        header_end = self.data.find(header_end_marker)
        if header_end == -1:
            return None

        header_section = self.data[:header_end].decode("ascii", errors="replace")
Step 1 — find the header/body boundary
HTTP-style headers are always terminated by a blank line, which on the wire is the byte sequence \r\n\r\n (carriage-return + line-feed, twice). bytes.find() does a raw byte-sequence search — this is the manual, from-scratch equivalent of Java's indexOf/array-scan; no multipart-aware library is doing this lookup for us.
Step 2 — decode only the header portion as text
Headers are guaranteed ASCII. The file's raw bytes (which could be anything — a JPEG, a zip, audio) are never decoded as text — only the slice before header_end is turned into a string. This is the key correctness detail: decoding the whole multipart body as text (which the original Java actually did, via new String(data)) risks corrupting bytes during the encode/decode round-trip; slicing first and only decoding the safe (ASCII) part avoids that risk entirely while keeping the same "search for markers in a string" approach. 
        filename_marker = 'filename="'
        filename_start = header_section.find(filename_marker)
        if filename_start == -1:
            return None
        filename_start += len(filename_marker)
        filename_end = header_section.find('"', filename_start)
        filename = header_section[filename_start:filename_end]
Step 3 — extract the filename by marker + quote scanning
Find the literal text filename=", skip past it, then find the next double quote — everything between those two positions is the filename. No regex, no parsing library: just two .find() calls and a slice. If the marker isn't present at all (not a file field), bail out with None. 
        content_type_marker = "Content-Type: "
        content_type_start = header_section.find(content_type_marker, filename_end)
        content_type = "application/octet-stream"
        if content_type_start != -1:
            content_type_start += len(content_type_marker)
            content_type = header_section[content_type_start:].strip()
Step 4 — extract Content-Type, with a sane default
Searching starts after filename_end so it can't accidentally match a Content-Type belonging to a different part. If the field genuinely has no Content-Type header (some browsers omit it for certain field types), fall back to application/octet-stream — "I don't know what this is, treat it as opaque binary." 
        content_start = header_end + len(header_end_marker)

        boundary_bytes = f"\r\n--{self.boundary}--".encode("ascii")
        content_end = self.data.find(boundary_bytes, content_start)

        if content_end == -1:
            boundary_bytes = f"\r\n--{self.boundary}".encode("ascii")
            content_end = self.data.find(boundary_bytes, content_start)

        if content_end == -1 or content_end <= content_start:
            return None

        file_content = self.data[content_start:content_end]
        return ParseResult(filename, content_type, file_content)
    except Exception as e:
        print(f"Error parsing multipart data: {e}")
        return None
Step 5 — the raw bytes start right after the blank line
content_start is just an integer offset — no copying happens yet.
Step 6 — find where the raw bytes end: the boundary
The multipart spec terminates the last part with \r\n--BOUNDARY-- (trailing double-dash) but a part in the middle of a multi-field form would instead be followed by \r\n--BOUNDARY (no trailing dashes, another part follows). The code tries the "final part" form first, and falls back to the "another part follows" form — this matters because FormData uploads from a browser often include more than one part (e.g. other form fields alongside the file).
Step 7 — this find is doing a binary-safe sequence search
Unlike the header section, self.data here is the full original bytes object — searching for boundary_bytes inside it is a byte-for-byte scan across what may be binary file content. This is exactly the manual "boundary sequence search" the original Java implemented as its own findSequence loop; Python's bytes.find is the same operation (a substring search over a byte array), just exposed as a built-in method rather than something we'd hand-loop ourselves — same level of "from scratch" as Java's own String.indexOf/array-scan calls.
Step 8 — slice out exactly the file bytes, nothing else
self.data[content_start:content_end] is a pure byte-offset slice — completely unaffected by anything that happened during the earlier ASCII-decode step, so binary files (images, zips, executables) survive intact. (This is verified in the worked example, §8, with a SHA-256 hash check.)
Step 9 — fail safe, never crash the server
Any unexpected exception (malformed input, missing boundary, whatever) is caught and turned into a logged message + None, which file_controller.py turns into a clean HTTP 400 response instead of a stack trace reaching the client.

6 p2p/file_controller.py

This is the HTTP layer — the glue between "a browser made a request" and the two pieces above (MultipartParser and FileSharer). It has five distinct pieces, in the order they execute conceptually.

6.1 ThreadPoolHTTPServer

class ThreadPoolHTTPServer(HTTPServer):
    def __init__(self, server_address, handler_class, max_workers: int = 10):
        super().__init__(server_address, handler_class)
        self.executor = ThreadPoolExecutor(max_workers=max_workers)

    def process_request(self, request, client_address):
        self.executor.submit(self._process_request_thread, request, client_address)

    def _process_request_thread(self, request, client_address):
        try:
            self.finish_request(request, client_address)
        except Exception:
            self.handle_error(request, client_address)
        finally:
            self.shutdown_request(request)

    def shutdown_and_wait(self):
        self.executor.shutdown(wait=True)
Step 1 — why subclass at all?
Plain http.server.HTTPServer is single-threaded: it accepts a connection, fully handles it via process_request, then loops back to accept the next one. Two clients can't be served at the same instant.
Step 2 — overriding the exact extension point
process_request(request, client_address) is the method the base class calls right after accept() succeeds. By overriding just this one method to hand the work to self.executor.submit(...) instead of running it inline, every other piece of http.server's machinery (request-line parsing, header parsing, routing to do_GET/do_POST) is untouched and still does its job — just now on a worker thread instead of the accept-loop thread.
Step 3 — finish_request / shutdown_request
These are the two halves process_request normally calls back-to-back: finish_request actually instantiates the handler class and runs the request; shutdown_request closes the socket afterward. Splitting them into their own thread function (_process_request_thread) and wrapping in try/except/finally ensures a single bad request can't crash a worker thread without closing its socket, or kill the server.
Why not just use socketserver.ThreadingMixIn?
That stdlib mixin would give you concurrency in one line — but it spawns a brand-new, uncapped thread for every single connection. The Java original deliberately used a fixed pool of 10 (Executors.newFixedThreadPool(10)) specifically to demonstrate bounded resource usage under load. ThreadPoolExecutor(max_workers=10) is the direct Python analogue of that exact design decision, so this file reimplements the dispatch loop instead of reaching for the one-line mixin.

6.2 peershareRequestHandler — routing & CORS

def do_OPTIONS(self):
    self.send_response(204)
    self._add_cors_headers()
    self.end_headers()

def do_POST(self):
    if self.path == "/upload" or self.path.startswith("/upload"):
        self._handle_upload()
    else:
        self._send_text(404, "Not Found")

def do_GET(self):
    if self.path.startswith("/download/"):
        self._handle_download()
    else:
        self._send_text(404, "Not Found")
Step 1 — do_GET/do_POST/do_OPTIONS are a stdlib convention
BaseHTTPRequestHandler automatically calls a method named do_<METHOD> matching the incoming HTTP verb. Defining only these three means any other verb (PUT, DELETE...) gets a built-in 501 automatically — we never have to handle that ourselves.
Step 2 — manual routing by string prefix
There's no router/framework — self.path.startswith(...) is the entire routing table. This mirrors the Java version's server.createContext("/upload", ...) / createContext("/download", ...) registration, just expressed as plain if/elif instead of a context map.
Step 3 — CORS and preflight
Because the UI runs on a different origin during development (Next.js on :3000 talking to this server on :8080), browsers send an OPTIONS preflight before the real POST. Responding 204 with the right Access-Control-Allow-* headers (in _add_cors_headers) is what lets the browser proceed with the actual request at all.

6.3 _handle_upload — tying the parser to the filesystem

def _handle_upload(self):
    content_type = self.headers.get("Content-Type")
    if not content_type or not content_type.startswith("multipart/form-data"):
        self._send_text(400, "Bad Request: Content-Type must be multipart/form-data")
        return

    try:
        boundary = content_type.split("boundary=", 1)[1]

        content_length = int(self.headers.get("Content-Length", 0))
        request_data = self.rfile.read(content_length)

        parser = MultipartParser(request_data, boundary)
        result = parser.parse()
        if result is None:
            self._send_text(400, "Bad Request: Could not parse file content")
            return

        filename = result.filename.strip() if result.filename else ""
        if not filename:
            filename = "unnamed-file"

        unique_filename = f"{uuid.uuid4()}_{os.path.basename(filename)}"
        file_path = os.path.join(self.server.upload_dir, unique_filename)

        with open(file_path, "wb") as f:
            f.write(result.file_content)

        port = self.server.file_sharer.offer_file(file_path)

        threading.Thread(
            target=self.server.file_sharer.start_file_server,
            args=(port,),
            daemon=True,
        ).start()

        self._send_text(200, json.dumps({"port": port}), content_type="application/json")
    except Exception as e:
        self._send_text(500, f"Server error: {e}")
Step 1 — validate Content-Type up front
Anything not announcing itself as multipart/form-data is rejected immediately — no point even trying to parse it.
Step 2 — pull the boundary string out of the header
The header looks like Content-Type: multipart/form-data; boundary=----WebKitForm... — everything after boundary= is the exact delimiter string the browser used between parts, and it's what gets handed to MultipartParser so it knows what to search for.
Step 3 — read exactly Content-Length bytes
self.rfile is a buffered stream over the live TCP socket. We can't just .read() until EOF (the connection might be kept alive for more requests) — we have to read precisely the number of bytes the client told us to expect.
Step 4 — hand bytes + boundary to the parser, bail cleanly on failure
This is the handoff into §5. A None result (malformed multipart body) becomes a clean 400, not a crash.
Step 5 — generate a collision-proof filename and write to disk
uuid.uuid4() generates a random 128-bit identifier; prefixing the original filename with it means two different uploads named photo.jpg never overwrite each other on disk, while os.path.basename(filename) strips any path components the client might have sent (defense against path traversal like ../../etc/passwd as a "filename").
Step 6 — claim a port, then start the listener in the background
offer_file (§4) returns synchronously with a port number. Starting start_file_server on its own thread is essential: that call accept()s and blocks (§4, Step 5) — if it ran here, the HTTP response below would never get sent because this thread would be stuck waiting for a peer to connect.
Step 7 — respond with the invite code
{"port": 51263} is the entire API contract the frontend depends on — that number is what gets shown to the user to share.

6.4 _handle_download — bridging HTTP to the raw socket protocol

def _handle_download(self):
    port_str = self.path.rsplit("/", 1)[-1]
    try:
        port = int(port_str)
    except ValueError:
        self._send_text(400, "Bad Request: Invalid port number")
        return

    try:
        with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as peer_socket:
            peer_socket.connect(("localhost", port))
            ...
            header_bytes = bytearray()
            while True:
                b = peer_socket.recv(1)
                if not b or b == b"\n":
                    break
                header_bytes += b
            header = header_bytes.decode("utf-8", errors="replace").strip()
            if header.startswith("Filename: "):
                filename = header[len("Filename: "):]

            while True:
                chunk = peer_socket.recv(UPLOAD_CHUNK_SIZE)
                if not chunk:
                    break
                tmp_file.write(chunk)
            ...
            with open(tmp_path, "rb") as f:
                while True:
                    chunk = f.read(UPLOAD_CHUNK_SIZE)
                    if not chunk:
                        break
                    self.wfile.write(chunk)
Step 1 — the port is the URL's last path segment
GET /download/51263 → rsplit("/", 1)[-1] → "51263". No routing framework needed for a path parameter this simple.
Step 2 — open a brand-new socket to itself
This is the conceptual hinge of the whole app: the browser never talks to port 51263 directly. It asks the API server (port 8080) to download, and the API server — acting as a client this time — opens its own raw TCP connection to localhost:51263, the same listener that FileSharer.start_file_server opened in §4.
Step 3 — read the filename header one byte at a time
Recall the sender (§4) writes b"Filename: cat.png\n" with no length prefix. The only safe way to know where that line ends without a length prefix is to read byte-by-byte until hitting \n — reading in a bigger chunk risks reading past the newline and swallowing the start of the actual file bytes along with it.
Step 4 — stream the rest straight to a temp file
Once the header line is consumed, every remaining byte on this socket is pure file content. It's buffered to a temp file (not memory) in UPLOAD_CHUNK_SIZE (4096-byte) reads — same chunk size convention as the sender side, again to avoid holding a potentially huge file fully in RAM.
Step 5 — re-stream the temp file back out over HTTP
Now acting as an HTTP server again, it sets Content-Disposition: attachment; filename=... (this is what makes the browser show a save-file dialog with the right name) and Content-Length (now known exactly, since the file is fully on disk), then pumps the temp file's bytes into self.wfile — the live response stream back to the browser — in the same 4096-byte chunks.
Step 6 — clean up
The temp file is deleted in a finally regardless of success or failure, so repeated downloads don't leak files into the OS temp directory.
Why round-trip through a temp file instead of streaming peer→browser directly?
It mirrors the original Java design exactly, and it has a real benefit: the browser doesn't get a response at all (not even headers) until the entire file has been pulled from the peer socket — so a slow or flaky peer connection can't leave the browser hanging on a half-started download with no Content-Length to show progress against.

6.5 FileController — wiring it all together

class FileController:
    def __init__(self, port: int):
        self.file_sharer = FileSharer()
        self.upload_dir = os.path.join(tempfile.gettempdir(), "peershare-uploads")
        os.makedirs(self.upload_dir, exist_ok=True)

        self.server = ThreadPoolHTTPServer(("", port), peershareRequestHandler, max_workers=10)
        self.server.file_sharer = self.file_sharer
        self.server.upload_dir = self.upload_dir

    def start(self):
        self._serve_thread = threading.Thread(target=self.server.serve_forever, daemon=True)
        self._serve_thread.start()

    def stop(self):
        self.server.shutdown()
        self.server.shutdown_and_wait()
        self.server.server_close()
Step 1 — one shared FileSharer for the whole process
Created once here, not per-request — so its available_files dict accumulates every upload/port mapping across the server's whole lifetime.
Step 2 — attaching shared state to the server object
BaseHTTPRequestHandler creates a brand-new handler instance for every single request — there's no natural place on the handler itself to keep long-lived state. The fix: stash file_sharer and upload_dir as attributes on self.server (the one long-lived HTTPServer instance, accessible from any handler as self.server), which both _handle_upload and (indirectly) the rest of the app rely on.
Step 3 — serve_forever on its own daemon thread
serve_forever() is a blocking call (it loops accepting connections until told to stop). Running it on a background thread is what lets app.py's main thread stay free to wait on input() for the user to press Enter.
Step 4 — graceful shutdown order matters
server.shutdown() stops the serve_forever accept loop; shutdown_and_wait() then waits for any in-flight worker threads in the pool to actually finish; only then is server_close() called to release the listening socket. Doing it in the wrong order could close the socket out from under a thread still using it.

7 app.py

def main():
    try:
        file_controller = FileController(8080)
        file_controller.start()

        print("peershare server started on port 8080")

        def handle_shutdown(signum, frame):
            file_controller.stop()
            sys.exit(0)

        signal.signal(signal.SIGINT, handle_shutdown)
        signal.signal(signal.SIGTERM, handle_shutdown)

        print("Press Enter to stop the server")
        input()
        file_controller.stop()
    except OSError as e:
        print(f"Error starting server: {e}", file=sys.stderr)
        sys.exit(1)
Step 1 — start, then immediately return control
file_controller.start() returns right away (it just launches the background thread from §6.5 Step 3) — it does not block.
Step 2 — two ways to stop, mirroring Java's shutdown hook
The Java original registered a JVM shutdown hook (fires on Ctrl+C or kill signal) and blocked on System.in.read() waiting for Enter. Python has no shutdown-hook equivalent, so this registers OS signal handlers for SIGINT (Ctrl+C) and SIGTERM (e.g. kill, or a container orchestrator stopping the process) that both call file_controller.stop(), while the main thread separately blocks on plain input() for the "press Enter" path.
Step 3 — startup failure handling
If port 8080 is already in use, FileController.__init__ → HTTPServer.__init__ raises OSError (e.g. [Errno 98] Address already in use), which is caught here and turned into a clean error message + exit code 1, instead of a raw traceback.

8 Trace a real upload + download

Here's the whole system worked through with concrete values, the way you'd trace through a recursive function by hand.

Given: the server is running (python app.py), and a browser uploads a 3-byte text file called hi.txt containing the bytes h, i, !.
Step 1 — the browser builds the multipart body
Axios/FormData constructs (boundary shortened to X for legibility): 
--X
Content-Disposition: form-data; name="file"; filename="hi.txt"
Content-Type: text/plain

hi!
--X--
and sends POST /upload with header Content-Type: multipart/form-data; boundary=X.
Step 2 — do_POST routes to _handle_upload
self.path == "/upload" matches. boundary = "X" is extracted from the header. self.rfile.read(content_length) pulls in the exact body shown above as raw bytes.
Step 3 — MultipartParser.parse() runs
  • header_end = index of \r\n\r\n → right after the Content-Type: text/plain line.
  • filename = text between filename=" and the next " → "hi.txt".
  • content_type = "text/plain".
  • content_start = the byte position right after the blank line — pointing at the h in hi!.
  • Search for \r\n--X-- (final-part form) finds it right after hi! → content_end set there.
  • file_content = data[content_start:content_end] = exactly the 3 bytes hi!.
Step 4 — saved to disk
Say uuid.uuid4() produces a1b2.... The file is written to <tmp>/peershare-uploads/a1b2..._hi.txt containing exactly hi!.
Step 5 — a port is claimed
upload_utils.generate_code() rolls, say, 52777. It's not in available_files yet, so it's registered: available_files[52777] = ".../a1b2..._hi.txt".
Step 6 — the one-shot listener spins up on a background thread
A new socket.socket() binds to ("", 52777) and calls listen(1), then blocks on accept(). Meanwhile, the HTTP response {"port": 52777} is sent back to the browser — the whole upload request is now complete, even though nobody has downloaded anything yet.
Given: someone (could be the same browser, could be a phone on the same network) now requests GET /download/52777.
Step 7 — do_GET routes to _handle_download
port = int("52777"). A new socket is opened: peer_socket.connect(("localhost", 52777)).
Step 8 — that connect() is exactly what accept() from Step 6 was waiting for
start_file_server's blocked accept() returns with the new connection. It launches _send_file on another thread, which writes: b"Filename: a1b2..._hi.txt\n" followed immediately by the 3 raw bytes hi!, then closes its socket.
Step 9 — the download handler reads it back
Reads byte-by-byte until \n → recovers filename = "a1b2..._hi.txt". Then recv(4096) returns b"hi!" (3 bytes — shorter than the buffer size, which is fine, that's normal TCP behavior), writes it to a temp file. The next recv() call returns b"" (peer closed the connection) → loop ends.
Step 10 — re-served over HTTP
Content-Disposition: attachment; filename="a1b2..._hi.txt", Content-Length: 3, then the 3 bytes hi! are written to self.wfile. The temp file is deleted. The browser shows a save dialog and saves a 3-byte file containing exactly hi!.
Answer
The 3 original bytes (h, i, !) survive two full protocol hops — multipart-over-HTTP in, then a hand-rolled-header-over-raw-TCP out — completely unchanged. This was verified for real during development with a 50 KB random binary file: SHA-256 of the file before upload and after download matched exactly, confirming the byte-slicing in the multipart parser (§5, Step 8) and the chunked socket transfer (§4) introduce zero corruption.

9 Why it's built this way (recap)

Things deliberately not hand-rolled
  • HTTP request-line/header parsing — http.server (stdlib), matching the original's use of the JDK's own HttpServer.
  • ParseResult boilerplate — @dataclass (pure bookkeeping).
  • UUIDs, JSON encoding, temp file creation — all stdlib utility, not part of the protocol being taught.
Things deliberately hand-rolled
  • Locating filename/Content-Type/boundary inside a multipart body — manual byte/string scanning, no cgi/email/python-multipart.
  • The entire P2P transfer — raw socket.socket(), a custom one-line text header, manual chunked read/write loops.
  • The bounded worker thread pool dispatching HTTP connections — a manual process_request override, not ThreadingMixIn.

10 Glossary

Socket
An OS-level handle representing one end of a network connection. socket.socket(AF_INET, SOCK_STREAM) creates a TCP/IPv4 one.
bind / listen / accept
The three steps a TCP server takes: claim a local address (bind), start queueing incoming connections (listen), then pull one off the queue and get a socket connected to that specific client (accept).
connect
The client-side counterpart to accept — actively opens a connection to a listening server's address.
TIME_WAIT / SO_REUSEADDR
After a TCP connection closes, the OS holds the port briefly to catch stray packets. SO_REUSEADDR lets a new socket bind to that port anyway.
multipart/form-data
The MIME content type browsers use to encode file uploads — a text-delimited envelope (boundary string) wrapping one or more parts, each with its own small header block and raw body.
Boundary
A unique delimiter string (chosen by the browser) that separates parts in a multipart body and marks the end of the whole body (with a trailing --).
Daemon thread
A background thread that doesn't keep the process alive on its own — if the main thread exits, daemon threads are killed without waiting for them.
Thread pool / Executor
A fixed set of reusable worker threads that pick up submitted jobs from a queue, instead of spawning a brand-new thread per job (which has no upper bound on concurrency).
Dynamic/ephemeral ports
Ports 49152–65535, set aside by IANA for short-lived, ad-hoc use rather than fixed/well-known services.
Content-Length / Content-Disposition
HTTP response headers: the former tells the client exactly how many bytes to expect; the latter (with attachment; filename=...) tells the browser to save the response as a file with that name instead of rendering it.
